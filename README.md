# Morgue Room Horror — 프로그래밍 포트폴리오

> Unity로 제작한 **호러 게임 프로그래밍 포트폴리오**입니다.
> "게임을 만들었다"가 아니라, **"이런 게임 기능을 직접 구현할 수 있다"**를 코드와 시연으로 보여주는 것이 목적입니다.

---

## 📌 한 줄 소개

『8번 출구』 스타일의 관찰 기반 호러 —
**3x3 무한 재활용 격자 트릭**과 **랜덤 이상현상 판별 시스템**을
직접 구현·시연하는 1인칭 호러 게임 프로그래밍 포트폴리오.

---

## 🎯 이 포트폴리오의 목적

이 프로젝트는 **기획·아트 포트폴리오가 아니라 프로그래밍 포트폴리오**입니다.

- 완성된 상용 게임을 목표로 하지 않습니다.
- **"게임 기능을 어떻게 설계하고 구현했는가"**를 코드와 시연으로 증명하는 것이 목표입니다.
- 그래서 **넓고 얕게 기능을 나열하기보다, 핵심 기능 하나(공간 반복 트릭)의 구현 완성도**에 집중합니다.

> 보는 사람이 궁금해할 질문은 하나입니다 —
> *"이 사람은 어떤 게임 시스템을, 어떤 방식으로 코딩할 수 있는가?"*
> 이 포트폴리오는 그 질문에 답합니다.

## 🧭 기반 컨셉 — 『8번 출구』 스타일

게임의 **기반(뼈대)**은 인기 호러 게임 **『8번 출구 (The Exit 8)』**의 구조에서 가져옵니다.

『8번 출구』의 핵심 재미는 다음과 같습니다:

- 공간을 **돌아다니며 주변을 관찰**하고, "이상현상(異変)"이 있는지 판단한다.
- **이상현상을 발견하면** 왔던 길로 되돌아가고, **없으면** 앞으로 전진한다.
- 이 판단을 반복하며 다음 구역으로 나아간다.

이 구조는 **관찰 → 판단 → 반응**이라는 단순하지만 강한 긴장감의 루프를 만듭니다.
본 포트폴리오는 **관찰 → 판단** 루프는 그대로 가져오되, "반응"에 해당하는 이동
구조는 8번 출구의 되돌아가기·전진(1D, 2택)이 아니라 **3x3 격자를 걸어서 넘나드는
방식**으로 바꿨습니다 — 나가는 문은 넷 중 아무 쪽이나 상관없고, 판단이 맞았는지
틀렸는지만 진행도에 반영됩니다. 프로젝트의 에셋(Morgue Room)을 살려 지하철
통로가 아닌 **영안실/시체안치소의 공간을 반복해서 돌아다니는** 무대로 옮겼습니다.

> **8번 출구에서 가져온 것과 버린 것 —** 관찰해서 이상현상을 판별하는 루프는 그대로
> 가져왔지만, "이상현상이 있으면 왔던 길로 되돌아간다"는 2택 규칙은 버렸다. 그
> 규칙이 성립하려면 공간이 1D 복도여야 하는데, 3x3 격자는 사방으로 열려 있어
> 되돌아간다는 개념 자체가 없다 — 대신 어느 문으로 나가든 판정 결과만 쌓인다.

## ⭐ 핵심 기능 — "3x3 무한 재활용 격자" 트릭 (메인)

이 포트폴리오의 **주 기능이자 하이라이트**는
뱀서식 무한 맵 재활용 기법을 1인칭에 이식해 만든
**끊김도 순간이동도 없이, 걸어서 무한히 나아가는 공간 트릭**입니다.

플레이어는 계속 새로운 방을 걸어서 지나간다고 느끼지만,
실제로는 **9칸짜리 격자가 등 뒤에서 조용히 재활용**되고 있습니다.
암전도 순간이동도 없습니다 — 카메라는 그 자리 그대로 있고, 타일(칸) 쪽이 움직입니다.

> **왜 바꿨나 —** 이 맵 전환 방식이 이 포폴의 **주 기능**인데, 내가 만든 다른
> 포폴들과 비교해보니 이전 방식(이상현상 판별 → 문 열고 복도로 나감 → 페이드아웃 →
> 방금 그 방은 사라지고 다음 방이 생김)은 **난이도가 쉬운 편이라** 호러 게임
> 포폴의 핵심 기능으로 내세우기엔 뭔가 애매하다는 생각이 들어, 3x3 격자 방식으로
> 바꿨다.

### 공간 구조와 루프 (구현됨)

```
       북
   ┌───┬───┬───┐
서 │   │   │   │ 동     플레이어는 항상 중앙(5) 칸에
   ├───┼───┼───┤        서 있는 것으로 취급된다. 인접
   │   │ 5 │   │        칸으로 걸어 들어가면 배열이 한
   ├───┼───┼───┤        칸 굴러가고, 반대편에 뒤처진
   │   │   │   │        행/열이 재활용된다.
   └───┴───┴───┘
       남
```

1. **관찰** — 칸 안을 살펴 이상현상이 있는지 판단한다.
2. **판정** — 키패드에서 O/X. 판정 전엔 사방 문이 전부 잠긴다.
3. **개방** — 판정하면 사방 문 잠금이 풀린다. 나가는 문은 직접 E로 연다.
4. **재활용** — 인접 칸으로 걸어 들어가는 순간, 중심에서 두 칸 뒤처진 행/열
   전체가 진행 방향 세 칸 앞으로 옮겨간다("배열이 한 칸 굴러가는" 셈). 방금
   지나온 문이 곧장 닫혀, 재활용은 그 닫힌 문 뒤에서 일어나 화면엔 아무 일도
   안 일어난다.
5. **반복** — 새로 놓인 칸은 새 이상현상으로 다시 꾸며진다. 정답 +1 / 오답 0,
   8회 연속 성공 시 클리어.
6. **위협** — 오답이 3번 누적되면 다음 칸엔 추격자('그것')가 이상현상으로
   등장한다. 보이면 멈추고, 안 보면 다가온다. 경계 문을 닫으면 피신한다.

### 이 기능이 증명하는 프로그래밍 기술

| 기술 | 내용 |
|------|------|
| 🗺️ 내장 Grid 좌표계 | `UnityEngine.Grid`의 좌표 변환을 그대로 써서 배치·재활용 계산을 직접 수식으로 안 짜도 되게 함 |
| ♻️ 타일 재활용 알고리즘 | 중심에서 2칸 뒤처진 행/열을 진행 방향 3칸 앞으로 재배치하는 뱀서식 무한 맵 기법을 1인칭에 이식 |
| 🕶️ 문으로 은폐 | "모든 문은 기본 닫힘, 방금 지나온 문만 열림" 규칙으로 재활용 순간을 항상 닫힌 문 뒤에 가둔다 |
| 🚪 경계 문 1짝 통일 | 문을 북·동쪽에만 달아 모든 경계에 문이 정확히 한 짝만 서게 함(겹문 버그 방지) |
| 🔌 인터페이스로 시스템 공유 | `IAnomalyHost` 하나로 이전 시스템(3안 `RoomModule`)과 새 격자(`GridCell`)가 판정·이상현상 로직을 그대로 공유 |
| 🕵️ 위협도 같은 좌표계로 | 추격자 피신 규칙이 "칸 좌표 + 경계 문 상태"만으로 판단 — 새 트리거 없이 기존 `Door`·`Grid` 상태만 재사용 |
| 📐 한 변을 필드로 일반화 | 흩어진 매직 넘버(±1·2·3)를 `Radius` 하나에서 유도 — **"왜 3이면 충분한가"를 수식으로 설명**하고 5x5도 필드 하나로 돌려 보인다 |
| 📏 은폐를 계측한다 | `CoverageAudit`이 재활용 프레임마다 *사라지는 자리·나타나는 자리*를 검사 — "안 보인다"가 **주장이 아니라 결과(위반 0회)**가 된다. 추격자의 시야 판정 코드와 칸 소켓을 그대로 재사용(새 에셋 0) |

### 🎥 시연 방식 — "착시 + 원리"를 동시에

이 트릭의 핵심 시연은 **게임뷰와 씬뷰를 동시에** 보여주는 것입니다.

- **게임뷰**: 플레이어는 계속 새로운 방으로 나아가는 것처럼 보인다 → **착시(결과)**
- **씬뷰(위에서 본 시점)**: `GridManager`의 씬 뷰 기즈모가 방금 재활용된 줄을
  2초간 빨갛게 칠해, 실제로는 등 뒤의 칸이 재배치되고 있다는 게 드러난다 → **원리(구현)**

> 기획 포폴은 "플레이어가 속는 착시"를 보여주지만,
> **이 포트폴리오는 "그 착시를 엔진 레벨에서 어떻게 만들었는가"**를 그대로 증명하는 것을 목표로 합니다.

## 👁️ 서브 기능 — 랜덤 이상현상 판별 시스템

반복되는 각 공간에는 **이상현상(異変)이 있을 수도, 없을 수도** 있습니다.
이상현상은 **하나의 판정 시스템**으로 관리되며, 그 내용은 **여러 변형 중 랜덤**으로 등장합니다.

- **구현된 변형 4종:** 시체 소실 / 시체 이동(자세 변화) / 시체 증가 / **시체 서랍 전부 열림**
- 플레이어는 **관찰**로 이상현상을 감지하고, 키패드의 **O/X 판정 UI**로 "있다 / 없다"를 판단한다.
- 판정이 **맞으면 진행도 +1**, **틀리면 0으로 리셋**.

| 기술 | 내용 |
|------|------|
| 🎲 랜덤 이상현상 시스템 | AnomalyManager가 등록된 변형 중 랜덤 발동, 방 리셋 시 항상 정상 상태로 완전 복원 |
| 🧩 변형 확장 구조 | 추상 클래스 `Anomaly` 상속으로 변형 추가(Toggle형·Transform형·Slide형) — 매니저 코드 수정 없이 확장 (다형성) |
| 🖥️ 판정 UI | uGUI 버튼 이벤트로 O/X 입력, 열릴 때 커서 해제 + 1인칭 조작 잠금, 닫히면 복귀 (모드 전환 관리) |

> **설계 원칙:** 이상현상은 *"종류는 1개 시스템, 내용은 랜덤 N개"*로 만듭니다.
> 구현은 하나에 집중하되, 플레이는 매번 달라지도록 하기 위함입니다.

## 🔢 진행도 표시 UI — 월드 스페이스(디제틱) UI

현재 연속 성공 횟수를 **키패드 위에 물리적으로 박힌 표시**로 보여줍니다.
화면 구석 HUD가 아니라 **게임 세계 안에 실재하는 UI(디제틱 UI)**라, 플레이어가
키패드를 쳐다봐야 `1 / 8` 같은 숫자를 읽게 됩니다 — 8번 출구의 세계 내 표지판과 같은 방식.

### 작동 방식

- **월드 스페이스 Canvas**가 **활성 방을 따라다닌다**(`FollowActiveRoom`) → 건물이 좌우
  슬롯을 오가도 표시가 늘 키패드 위에 붙어 있다.
  - 🐛 원래는 캔버스가 씬 루트에 고정돼 있어, 건물이 반대편 슬롯에 서는 **짝수 회차마다
    표시가 사라졌다.** 처음 한 번 '활성 모듈 기준 상대 자세'를 기억해두고 매 프레임
    현재 모듈에 다시 적용하는 방식으로 해결.
- `GameManager`가 관리하는 진행도를 매 프레임 읽어 텍스트에 반영. **값 계산·판정은
  GameManager가, '표시'만 여기서** 담당한다 (관심사 분리 — `InteractionPromptUI`와 동일 철학).
- 판정 성공 시 `1 / 8 → 2 / 8` 로 올라가고, 오답이면 `1 / 8` 로 리셋, 목표 도달 시 `CLEAR`.

| 기술 | 내용 |
|------|------|
| 🌍 디제틱 UI | Screen Space HUD가 아닌 **World Space Canvas**를 키패드에 마운트 (렌더 모드 무관 스크립트) |
| 🔗 상태 참조 | `GameManager.Progress` / `ClearGoal`을 읽어 표시만 담당 (로직과 표현 분리) |
| 🔢 표시 오프셋 | `진행도 + 시작 번호(displayOffset)`로 0-기반 값을 **1-기반(`1/8`)** 표시로 변환 — 형식 문자열이 아닌 값으로 제어 |

> **설계 포인트:** 표시 형식(`{0} / {1}`)과 표시 값(진행도+오프셋)을 분리해,
> 시작 숫자를 바꿀 때 형식 문자열의 자리 번호를 건드리지 않고 **숫자 필드 하나로** 조절한다.

## 🕵️ 추격자 — 씬 구조로 푼 문제들

추격자를 넣은 직후 증상이 셋 있었다. **안 보인다 / 누운 채로 다가온다 /
쳐다봐도 안 멈춘다.** 셋 다 코드가 아니라 **씬 구조**가 원인이었고, 그래서
**코드가 아니라 씬으로 고쳤다.** 여기서 얻은 게 이 기능에서 제일 값진 부분이다.

### ① 안 보인다 + ② 누운 채로 다가온다 — 부모가 다른 로컬 좌표

`Stalker`가 등장 자리를 `spawnPoint`의 **로컬 좌표**로 읽고 있었는데,
`spawnPoint`와 추격자의 **부모가 서로 달랐다.** 좌표계가 다르니:

- **위치**가 부모 오프셋(5.4, -0.5, 0.8)만큼 어긋나 바닥 아래로 파묻혔다
- **회전**이 기준점의 무회전으로 덮여, 세워둔 자세(z 90°)가 지워져 **시체가 누웠다**

`TransformAnomaly`에 이미 적어둔 함정과 **똑같은 종류**다 — 로컬 복사는 부모가
같아야만 맞다. 그래서 등장할 때 기준점의 **월드** 자세를 읽도록 바꿨다.

회전 쪽은 코드로도 막을 수 있었지만(보정 쿼터니언을 따로 곱하는 식),
**구조로 푸는 쪽을 골랐다:**

```
Stalker        ← 로직용 루트. 무회전, 피벗은 발바닥. 회전을 덮어써도 안전
└── Model      ← 아트용. 세우는 보정(z 90°)을 여기가 들고 있는다
    └── 표본점(머리·가슴·발)
```

나누지 않으면 `LookRotation`이 매 프레임 보정을 지운다. 나누면 **계산 자체가 사라진다.**

### ③ 쳐다봐도 안 멈춘다 — 자기 몸이 시야를 막고 있었다

차폐 검사의 **출발점이 카메라**인데, 카메라는 **플레이어 몸 안**에 있다.
그래서 첫 히트가 플레이어 자신의 콜라이더로 잡혀, 정면으로 쳐다봐도 영영
"가려짐"이 나왔다. 소품(의자·세면대)까지 전부 시야를 막는 것도 겹쳤다.

**진단 방법 —** 판정이 바뀔 때만 콘솔에 한 줄 남기게 했더니 범인이 바로 나왔다.

```
[Stalker] 시야 판정 → 화면엔 있으나 가림 — Player · 거리 12.4m
[Stalker] 시야 판정 → 화면엔 있으나 가림 — metal_sink · 거리 12.4m
```

**해결 —** 콜라이더를 코드로 걸러내는 대신 **레이어**로 풀었다. `SightBlocker`
레이어를 만들어 **벽·문만** 넣고, 추격자의 `Occluders` 마스크를 그것만으로 좁혔다.

> **마스크는 "빼기"가 아니라 "넣기"로 설계했다.** `Default` 하나로 두면 세상 모든
> 것이 시야를 막아서 하나씩 빼내는 싸움이 된다. 반대로 두면 소품을 새로 추가해도
> 기본이 "안 막음"이라 같은 사고가 재발하지 않는다.

### ④ 물체를 통과한다 — 충돌 응답까지만

좌표를 직접 더하고 있어서 테이블을 관통했다. `CharacterController`로 바꿔
**막히면 표면을 타고 미끄러지게** 했다.

경로탐색은 **의도적으로 범위 밖**이다. `NavMeshSurface`로 두 슬롯을 함께 구우면
가능하긴 하지만, 이 기능에서 증명하려는 건 경로탐색이 아니라 시야 판정이다.
다만 **통과해버리면 '보고 멈춘다'는 규칙 자체가 우스워지므로** 충돌까지는 처리했다.
"어디까지 하고 어디서 멈출지"를 정한 선이 여기다.

### 이 과정에서 얻은 원칙

**씬 설정 문제를 코드로 때우면 버그가 늘어난다.** 실제로 이번에 콜라이더 필터링을
코드로 짰다가 걷어내고 레이어로 옮겼고, 회전 보정도 쿼터니언 계산에서 자식
오브젝트로 옮겼다. 둘 다 **코드가 줄고 사고 여지가 사라졌다.**

| 문제 | 코드로 때우면 | 엔진 기능으로 풀면 |
|---|---|---|
| 특정 콜라이더 제외 | 히트 순회하며 걸러내기 | **LayerMask** |
| 컴포넌트 필수 보장 | null 체크 분기 | **`[RequireComponent]`** |
| 모델 자세 보정 | 쿼터니언 오프셋 계산 | **자식 오브젝트** |

### 넣을 것 (우선순위 순)

| 대상 | 붙일 지점 | 비고 |
|---|---|---|
| 문 '쾅' 닫힘 | `Door.Slam()` | 반동까지 만들어놨으니 소리만 얹으면 완성 |
| 문 여닫힘 | `Door.Open()` / `Close()` | 경첩 삐걱임 |
| 발소리 | `FirstPersonController.HandleMovement()` | `IsMoving`으로 재생/정지 |
| 이상현상 발동 스팅어 | `AnomalyManager.SetAnomaly()` | 발동 순간 짧은 긴장음 |
| 앰비언스 | 씬 상시 재생 | 형광등 웅웅거림 — 정적을 채워 긴장 유지 |
| **오답 스팅어** ← 우선 | `ScareFlash.Flash()` | 그림은 이미 번쩍인다. **소리가 붙어야 완성되는 연출** — 지금은 절반만 된 상태 |
| 판정 성공/실패 | `GameManager.Judge()` | 위 스팅어와 함께 |

### 설계 메모

- 재생 로직을 각 스크립트에 흩뿌리지 말고, `IInteractable`·`Anomaly`처럼
  **작은 오디오 창구 하나**를 두고 거기에 위임하는 편이 일관된다 (관심사 분리).
- 코드 수정량 자체는 적다 — 대부분 `PlayOneShot` 한 줄 수준.

      안쪽 이중문이 **열린 채로 저장돼** 있어, 닫아도 그 자세로 돌아갔다.
      에디터에서 완전히 닫은 자세로 다시 잡아 해결 (코드 수정 없음)
- [x] 진행도 표시가 짝수 회차에도 보인다
- [x] 문 E 상호작용 — 레이어를 대량으로 바꾼 뒤에도 정상
- [x] 추격자가 테이블·모서리에 **끼지 않는다**
      → 다만 긴 테이블에 막히면 **돌아오지 못하고 밀리기만 한다.** 버그가 아니라
      충돌 응답이 회피가 아니라서 생기는 **알려진 한계**다. 가구가 엄폐물이 되는
      셈이라 그대로 뒀다 (경로탐색은 의도적으로 범위 밖 — 위 "추격자" 섹션 참고)

### 2. 이상현상 추가 (여유 있으면)

`ToggleAnomaly` / `SlideAnomaly`로 **코드 없이** 가능한 것들:

- 천장 조명 하나 꺼짐 (`ceiling_light` 6개 중 하나 → `hideOnActivate`)
- 소품 소실/증가 (`brain_jar`, `instrument_tray`, `trash_can`) — 시체보다 작아 난이도 높은 변형

> 변형이 늘수록 각 변형의 등장 확률은 낮아진다(4종이면 각 1/4).
> 너무 미묘한 것을 넣으면 플레이어가 못 찾고 억울하게 지므로, 눈에 띄는 것 위주로.

### 3. 튜닝

- `ScreenFader`: Fade Out / Hold / Fade In 시간
- `ScareFlash`: `Hold`(0.12) — 길면 그림을 뜯어보게 되어 안 무섭고, 짧으면 "방금 뭐였지?"가 남는다
- `Door`: `Slam Duration`(0.07) / `Slam Rebound Angle`(6°)
- `SeamTrigger` 위치: 문에서 멀수록 "걷다 보니 어두워졌다"가 자연스러움
- `FirstEntryPoint`: 게임 시작 시 서는 자리·바라보는 방향

### 씬 상태 주의사항 (유지할 것)

- **소켓은 통과하는 문이 아니라 기준점이다.** 칸 간격 실측(`MeasureSpacing`)과
  **은폐 검사의 표본점**(`CoverageAudit`)이 둘 다 여기에 달려 있다. 위아래로 기울이거나
  문 정중앙·벽 바깥면에서 떼어놓지 말 것 — 간격이 틀어지고 은폐 검사가 헛돈다.
- ~~`ParkAnchor` 삭제 금지~~ · ~~`SeamSocket`~~ — **3안 전용이라 함께 제거됐다.**
  (`RoomModulePool`·`RootAnchor`·`ParkAnchor`·`FadeCanvas`·`Clearimage`도 같이)
- **레이어 규칙** — 추격자 시야 판정 **과 은폐 검사**가 여기에 통째로 의존한다.
  - `SightBlocker` = **벽·문만.** 소품(의자·세면대)을 넣으면 그 뒤에서 안 멈춘다
  - ⚠️ `CoverageAudit`의 `Occluders`도 **`Stalker`와 같은 값**(`SightBlocker` 하나)으로
    둘 것. 비워 두면 아무것도 시야를 막지 않는 것이 되어 **위반이 쏟아진다**
  - `Player` = 플레이어. **`SightBlocker`에 넣지 말 것** — 카메라가 몸 안에 있어
    자기 몸이 시야를 막아 영영 '안 보임'이 된다
  - 추격자도 `SightBlocker` 밖에 둘 것 (`CharacterController` 캡슐이 자기 시야를 막는다)
- **추격자 `Model`의 Position은 `(0, 1.055, 0)`** — Y만. X/Z를 주면 **로직 위치와
  보이는 몸이 어긋나** 안 보이는 것에 잡힌다. 등장 자리는 `StalkerPoint`로 정한다.
- 안쪽 이중문은 **완전히 닫힌 자세로 저장**해야 한다 (`Door`가 그 자세를 '닫힘'으로 굳힌다).

### 1️⃣ 1인칭 컨트롤러 — `FirstPersonController.cs`

**기능:** WASD 이동 · 마우스 시점 회전(몸통 Yaw / 카메라 Pitch 분리) · 중력

| 사용한 함수·API | 용도 |
|----------------|------|
| `InputAction` + `AddCompositeBinding("2DVector")` | WASD 4키를 하나의 `Vector2` 입력으로 합성 |
| `moveAction.ReadValue<Vector2>()` | 매 프레임 이동 입력 읽기 |
| `CharacterController.Move()` / `.isGrounded` | 물리 이동 + 바닥 판정 |
| `transform.Rotate()` / `Quaternion.Euler()` | 몸통 좌우 회전 / 카메라 상하 기울임 |
| `Mathf.Clamp()` | 시점이 뒤로 넘어가지 않게 상하 각도 제한 |
| `Vector3.ClampMagnitude()` | 대각선 이동이 √2배 빨라지는 것 방지 |
| `Cursor.lockState` / `Cursor.visible` | 1인칭 조작감(커서 잠금·숨김) |

**설계 포인트:** Yaw(몸통)와 Pitch(카메라)를 분리해 몸은 수평 유지 → 시선 상하가 이동 방향에 영향을 주지 않는 1인칭 정석 구조. 이동 상태(`IsMoving`)와 조작 잠금(`ControlsLocked`)을 프로퍼티로 노출해 손 애니메이션·UI가 참조하게 함.

### 🖐️ 손 애니메이션 — `HandAnimator.cs`

**기능:** 걷기/정지에 따라 손 Idle ↔ Walk 전환

| 사용한 함수·API | 용도 |
|----------------|------|
| `GetComponentsInChildren<Animator>()` | 좌/우 손 Animator를 한 번에 수집 |
| `Animator.StringToHash("IsMoving")` | 파라미터 이름을 해시로 캐싱(매 프레임 문자열 비교 비용 제거) |
| `Animator.SetBool()` | 이동 여부를 Animator에 전달 |

**설계 포인트:** 이동 '판단'은 컨트롤러가, 애니메이션 '반영'은 여기서 → 로직과 표현(연출)을 분리.

### 2️⃣ 상호작용 시스템 — `PlayerInteractor.cs` + `IInteractable.cs`

**기능:** 카메라 정면을 조준해 상호작용 가능한 물체를 감지하고 E로 작동

| 사용한 함수·API | 용도 |
|----------------|------|
| `Physics.Raycast(ray, out hit, range, layerMask, QueryTriggerInteraction.Collide)` | 시선 정면·사거리 내 물체 감지 (트리거 콜라이더도 조준 대상에 포함) |
| `LayerMask` (Interactable 레이어) | 상호작용 대상 레이어만 필터링 |
| `hit.collider.GetComponentInParent<IInteractable>()` | 콜라이더가 자식(문짝)에 있어도 부모의 상호작용 컴포넌트 탐색 |
| `interactAction.WasPressedThisFrame()` | E 입력 감지 |

**설계 포인트:** 대상이 문인지 키패드인지 몰라도 `Interact()` 하나로 처리(인터페이스 다형성). 조준 대상의 안내 문구(`Prompt`)를 UI가 읽어가 화면에 표시. 조준 필터는 **레이어(Interactable)** 로 하고, 조준되면 안 되는 볼륨(복도 순간이동 트리거)은 다른 레이어에 두어 `LayerMask` 단계에서 제외한다.

**해결한 이슈 2건:**
- 🐛 **UI 열린 채 상호작용 유지** — 판정 UI가 열려 커서가 풀린 상태에서도 E로 문이 여닫히던 문제를, `JudgmentUI.IsOpen`일 때 상호작용을 멈추도록 가드를 추가해 해결.
- 🐛 **키패드가 조준되지 않음** — 키패드의 상호작용 콜라이더가 트리거(IsTrigger)라, 트리거를 무시하는 Raycast 설정에서는 조준되지 않던 문제를 `QueryTriggerInteraction.Collide`로 트리거도 잡도록 명시해 해결.

### 🚪 코드 제어 문 — `Door.cs`

**기능:** 경첩식으로 부드럽게 여닫힘. **플레이어용(E 토글)과 시스템용(자동 개폐)을 한 클래스로**

| 사용한 함수·API | 용도 |
|----------------|------|
| `StartCoroutine` / `StopCoroutine` + `IEnumerator` | 프레임에 걸친 문 회전 애니메이션 |
| `Quaternion.Slerp()` | 현재 각도 → 목표 각도 부드러운 보간 |
| `Quaternion.AngleAxis()` | 경첩 축 기준 열림 각도 계산 |

**설계 포인트:** `Interact()`는 잠금(`isLocked`)을 존중하지만, `Open()`/`Close()`는 코드 전용이라 잠금을 무시 → 평소엔 못 여는 복도 문을 `GameManager`가 직접 여닫음. 보간을 현재 각도에서 시작해 여닫는 중간에 방향이 바뀌어도 자연스러움.

### 3️⃣ ⭐ 공간 반복 트릭 — 3x3 무한 재활용 격자

> 관련 스크립트: `GridManager.cs` · `GridCell.cs` · `Door.cs` · `IAnomalyHost.cs`

**기능(메인):** 걸어서 옆 칸으로 넘어가면, 등 뒤로 두 칸 뒤처진 행/열 전체가
진행 방향 세 칸 앞으로 재배치된다 — 암전도 순간이동도 없이 무한히 걷는 착시.
자세한 설계 배경·시행착오·규칙은 아래 "🔲 3x3 격자" 섹션에 전부 있다. 여기서는
핵심 함수·API만 정리한다.

| 사용한 함수·API | 용도 |
|----------------|------|
| `Grid.CellToWorld()` | 칸 좌표 → 월드 좌표 변환. 직접 수식을 안 짜고 Unity 내장 격자에 맡긴다 |
| `Transform.InverseTransformPoint()` + `Mathf.RoundToInt()`(커스텀 `GetCoordAt()`) | 월드 좌표 → 칸 좌표 역변환. `Grid.WorldToCell()`은 칸의 모서리를 경계로 가정해 방 프리팹(원점이 방 중앙)엔 안 맞아 직접 보완했다 |
| `Dictionary<Vector2Int, GridCell>` | 지금 격자에 놓인 칸을 좌표로 관리 — 재활용 때 좌표만 바꿔치기 |
| `event Action<GridCell>`(`Initialized`/`CenterChanged`/`CellRecycled`) | `GridManager`는 "칸이 어디 있는가"만 알고 "그 칸에 뭘 채울까"는 모른다 — 이벤트로 `GameManager`에 위임(관심사 분리) |
| `Door.IsOpen` + `GridCell.GetDoors(Vector2Int)` | 추격자 피신 판정 — 경계 문 상태만 읽어 별도 트리거 없이 안전 여부를 계산 |

**설계 포인트 ① — 좌표를 손으로 안 찍는다.** 배치·재활용·피신 판정까지 전부
`UnityEngine.Grid`의 좌표 변환에 얹었다. 칸 크기가 바뀌어도 씬을 다시 잴 필요가 없다
(`RoomSocket` 실측 패턴과 같은 철학).

**설계 포인트 ② — 재활용은 배열이 한 칸 굴러가는 것.** 중심에서 반대편으로 두 칸
뒤처진 행/열을 진행 방향 세 칸 앞으로 옮긴다. 뱀서식 무한 맵 기법을 1인칭에 그대로
이식한 부분이다.

**설계 포인트 ③ — `IAnomalyHost`로 신·구 시스템이 한 로직을 공유한다.** 이전 방식
(`RoomModule`)과 격자(`GridCell`)가 서로 다른 클래스라도, `GameManager`의
`Judge()`/`Dress()`는 인터페이스 하나만 보고 똑같이 동작한다(다형성).

### 공간 반복 트릭(이전 방식, 3안) — 방 모듈 풀링 + 좌우 슬롯 교대

> 관련 스크립트: `RoomModulePool.cs` · `RoomModule.cs` · `RoomSocket.cs` · `SeamTrigger.cs` · `ScreenFader.cs` · `PlayerTeleporter.cs`
>
> ⭐는 위 3x3 격자로 넘어갔다 — 이 섹션은 격자 이전에 썼던 방식과 그 시행착오
> 기록이다. `gridMode`를 끄면 지금도 이 경로로 동작한다.

**기능:** 판정 후 복도를 걷다 보면 화면이 암전되고, 밝아지면 다시 영안실 문 앞.
그 암전 사이에 **건물이 통째로 반대편으로 옮겨간다.**

```
판정 → 복도 문 열림 → 복도를 한참 걸음 → SeamTrigger
     → ScreenFader 페이드아웃
     → ▓▓ 완전 암전 ▓▓  ① 현재 건물 컬링(SetActive false) + 대기 위치로
                        ② 다음 건물을 반대쪽 슬롯에 세우고 활성화
                        ③ 플레이어를 새 건물 복도 문 앞으로 스냅
     → 페이드인 → 다시 영안실 문 앞
```

**화면에 존재하는 건물은 언제나 하나뿐이다** — 이것이 이 설계의 핵심 제약이자 강점.

#### 여기까지 온 시행착오 (4안 중 3안 채택)

| 시도 | 방식 | 폐기 사유 |
|------|------|----------|
| 1안 | 방 하나를 통째로 이동 (`RoomLoopMover`) | 방이 하나뿐이라 **자기 자신과 겹침** |
| 2안 | 방 2개를 복도 끝끼리 이어붙임 (소켓 체인) | 두 건물이 동시에 존재 → **이음새를 들킴** |
| **3안** | **한 번에 하나만 + 좌우 슬롯 교대** | **채택** — 동시 존재 자체를 없앰 |
| 4안 | 복도 끝에 U턴 코너를 두고 **암전 없이 걸어서** 넘어감 | **가능하나 보류** — 아래 참고 |
| **5안** | 4안 + **무한 맵 청크 재활용**(강사님 제안) | **다음 본작업** — 아래 참고 |

2안은 순간이동도 암전도 없이 "진짜로 걸어서" 이동하는 구조라 기술적으로는 더 매끄러웠지만,
복도 저 끝에 반대편 건물이 실제로 서 있다는 사실을 **눈썰미 좋은 플레이어는 알아챈다.**
착시는 "티가 안 나는 것"이 전부라, 기술적 우아함보다 **들키지 않는 쪽**을 택했다.

#### 4안 — 가능하지만 하지 않기로 한 것

먼저 **2안의 진단이 반쯤 틀렸다.** 2안이 들킨 원인은 "두 건물이 동시에 존재해서"가 아니라
**복도가 직선이라 저 끝이 보여서**였다. 시야를 꺾는 오클루더(코너)를 하나 넣으면 동시 존재
자체는 문제가 되지 않는다. 『8번 출구』가 정확히 그 방식이다 — 암전이 아니라 **U턴 코너**로
이음새를 가리고, 플레이어가 코너를 도는 사이 등 뒤의 복도를 조용히 리셋한다.

그래서 4안은 기술적으로 성립한다. 배치 계산(`AlignSeamTo`)도 그대로 쓸 수 있다 — 소켓을
막다른 벽에서 코너 출구로 옮기기만 하면 된다. 게다가 모듈이 런타임에 움직이지 않고 두 슬롯에
고정되므로, 지금은 쓰지 못하는 **Occlusion Culling·NavMesh 베이킹이 가능해진다**
(둘 다 Static 오브젝트만 대상이라, 좌표가 매 루프 바뀌는 현재 구조에서는 애초에 못 굽는다).

그럼에도 하지 않았다. **`pool.Active`가 하나뿐이라는 제약이 이미 다섯 군데를 떠받치고 있다.**

| 기대는 곳 | 이 제약에서 무엇을 공짜로 얻고 있나 |
|---|---|
| `Judge()` | `pool.Active.HasAnomaly` — **어느 방의** 정답인지 물을 필요가 없다 |
| `PlayerIsSheltered` | **어느 방의** 문을 검사할지 따질 필요가 없다 |
| `FollowActiveRoom` | 진행도 UI가 따라갈 방이 자명하다 |
| `DismissStalker` / `ResetInteriorDoors` | Active에만 걸면 충분하다 |
| **`Stalker.Update()`** | **비활성 모듈은 `SetActive(false)`라 아예 돌지 않는다** |

마지막 줄이 결정적이다. **추격자가 한 마리인 이유가 컬링이다.** 두 모듈을 동시에 켜는 순간
추격자도 둘이 되어 빈 방에서 혼자 걸어다니고, 나머지 넷도 "어느 방?"을 새로 정해야 한다.
코너를 붙이는 작업이 아니라 **검증이 끝난 기능 다섯 개를 다시 여는 일**이다.

> **"화면에 존재하는 건물은 언제나 하나뿐"은 편의가 아니라 하중 벽이었다.**
> 3안을 고를 때는 이음새를 감추려고 세운 제약이었는데, 그 위에 기능이 넷 더 올라가면서
> 구조가 됐다. 제약을 걷어내려면 그 위에 지은 것을 전부 다시 세워야 한다는 걸,
> **걷어내려다 알았다.**

경로탐색을 범위 밖에 둔 것(위 "추격자" 참고)과 같은 종류의 판단이다 —
**못 하는 게 아니라, 여기에 값을 치르지 않기로 한 것이다.**

### 🔜 5안 — 무한 맵 재활용을 1인칭에 이식 (다음 본작업)

강사님이 **2D 탑다운 무한 맵 기법**을 알려주셨다. 예시로 든 게임은 뱀파이어 서바이버즈.
셀을 3x3으로 깔고 플레이어를 늘 한가운데 두다가, 중심이 옮겨가면 **등 뒤에 남은 셀을
앞으로 순간이동**시켜 재활용한다. 9칸으로 무한히 걸을 수 있다.

```
   1 2 3          5 → 2 로 이동하면
   4 5 6      →   7 8 9 가 통째로 위로 올라가 새 윗줄이 된다
   7 8 9          (배열이 한 칸 굴러간 셈)
```

**기법 자체는 표준이 맞다.** 오픈월드 지형 스트리밍(Minecraft, No Man's Sky)과
엔드리스 러너(Temple Run)가 전부 이 구조다. 문제는 **그대로 옮겨오면 들킨다**는 것이다.

| 뱀서에서 안 들키는 이유 | 이 게임 |
|---|---|
| **탑다운 고정 카메라** — 보이는 범위가 화면으로 잘려 3x3이면 늘 충분 | **1인칭** — 고개만 돌리면 어디든 본다. 잘리는 경계가 없다 |
| 타일이 반복되는 바닥이라 **원래 다 똑같이 생겼다** | 방이 또렷하고 **외워야 하는** 공간. 티가 나는 것이 게임의 전부다 |
| 가릴 것이 애초에 없다 (내려다보는 평면) | **가리는 것이 유일한 과제다** |

즉 뱀서는 **은폐가 공짜다.** 카메라가 알아서 잘라준다. 1인칭은 그 공짜가 없어
은폐층을 직접 만들어야 하고, 그것이 4안의 **코너**다. 그래서 이렇게 나눠 가져온다.

| 무엇을 | 어디서 |
|---|---|
| 재활용 구조 (등 뒤 셀을 앞으로 돌려쓰기) | **강사님 방식 그대로** |
| 은폐 | **코너 오클루전** — 뱀서의 화면 경계를 대신한다 |
| 차원 | **1D** — 방이 문으로 이어져 있어 대각선 이동이 물리적으로 불가능하다 |

#### 4방향 격자는 왜 버렸나 — 장르가 거부한다

처음에는 강사님 그림 그대로 **정사각 셀 + 사방 문 4개**를 검토했다.
기술적으로는 성립하지만 **이 게임의 장르가 그것을 거부한다.**

- **관찰 게임은 방을 외워야 한다.** "시체가 하나 사라졌다"를 알아채려면 방이 또렷하고
  비대칭이어야 한다. 정사각 대칭 방에 똑같은 문 4개는 **방향감각을 일부러 무너뜨리는**
  설계다 — 미로의 문법이지 관찰의 문법이 아니다.
- **8번 출구 규칙은 2택이라 무게가 있다.** "이상현상이 있으면 되돌아간다"가 긴장인 것은
  선택지가 둘뿐이기 때문이다. 4택이 되면 판정이 **어디로 갈지 고르는 문제에 묻힌다.**
- **추격자는 복도가 있어야 산다.** 셀을 방 한 칸으로 줄이면 등 뒤에서 좁혀올
  **거리가 안 나온다.**
- **문을 오클루더로 쓰면 던전이 된다.** 문을 여는 순간 다음 칸이 통째로 보인다.
  호러는 코너로 꺾어 가리는 것이지, 문짝으로 딱 자르는 것이 아니다.

> **기법을 배웠으면 전제 조건까지 배워야 한다.** 뱀서의 3x3이 성립한 것은 격자가
> 훌륭해서가 아니라 **카메라가 탑다운이었기 때문**이다. 카메라를 바꾸면 그 전제가
> 무너지고, 무너진 자리를 다른 것으로 메워야 한다.

#### 4안을 접었던 판단은 왜 뒤집혔나

4안을 보류한 이유는 "`pool.Active`가 하나라는 제약이 다섯 군데를 떠받친다"였고,
**그 진단 자체는 지금도 유효하다.** 바뀐 것은 두 가지다.

- **값이 오를 만해졌다.** 지금 포폴의 가장 큰 약점은 결국 **암전으로 가린다**는 것이다.
  코너로 넘어가면 그 목발이 없어지고 **진짜 심리스**가 된다.
- **제일 큰 벽의 해법이 분명해졌다.** 다섯 군데 중 결정적인 것은 추격자였는데,
  **추격자를 모듈 소속에서 씬 소속으로 올리면** 모듈이 몇 개 켜지든 한 마리다.
  나머지 넷은 "어느 방?"을 `Current` 하나로 답하면 끝난다.

#### 작업 순서 — 무엇부터 쌓나

**되돌릴 수 있는 조각으로 자르는 것**이 이 작업의 핵심이다. 3안은 이미 완성품이라,
5안이 막히더라도 3안이 그대로 남아 있어야 한다.

| # | 할 일 | 왜 이 순서인가 |
|---|---|---|
| 0 | **3안 시연 영상을 먼저 찍어둔다** | 5안이 막히면 이것이 포폴이다. **보험을 들고 시작한다** |
| 1 | **추격자 승격** — `RoomModule`의 자식 → 씬 단일 존재 | 유일한 하드 블로커. **3안 위에서도 그대로 돌아가** 단독 커밋·단독 테스트가 된다 |
| 2 | **DebugPanel에 검증 줄** — 활성 모듈 수 / 추격자 수 | 모듈이 2개 켜지는 순간을 **눈으로** 봐야 한다. 추격자 연결 누락을 잡아준 그 표시판과 같은 역할 |
| 3 | **씬: 복도 끝 막힌 벽 → ㄱ자 코너**, 소켓을 코너 출구로 이동 | 코드 없이 에디터만으로 된다. `AlignSeamTo`가 소켓을 따라가므로 **배치 코드를 안 고쳐도 된다** (설계 포인트 ①이 여기서 값을 한다) |
| 4 | **체인 배치** — 좌우 슬롯 교대 → 두 모듈을 코너로 이어붙이기 | 여기서 **처음으로 모듈 2개가 동시에 켜진다.** 1·2가 끝나 있어야 안전하다 |
| 5 | **암전 제거** — `SeamTrigger` · `FadeThrough` · `PlayerTeleporter` 철거 | 진짜로 걸어서 넘어가므로 순간이동 자체가 없어진다. `ScreenFader`는 클리어 연출용으로 남긴다 |
| 6 | **`Current` 기준 재배선** — `Judge` · `PlayerIsSheltered` · `FollowActiveRoom` · `ResetInteriorDoors` | 넷 다 "어느 방?"만 답하면 된다 |

**브랜치를 딴다.** `main`은 3안이 플레이 테스트를 전부 통과한 상태다.
`feature/seamless-room-chain`을 썼던 전례대로 따로 딴 뒤, 통과하면 병합한다.

> **1번이 전체의 절반이다.** 나머지는 배선을 갈아끼우는 일에 가깝지만, 추격자는
> "비활성 모듈은 `SetActive(false)`라 Update가 안 돈다"는 **우연에 기대고 있던 것**을
> 의도로 바꾸는 일이라 설계가 바뀐다. 여기가 뚫리면 나머지는 따라온다.

### 🔲 3x3 격자 — 5안에서 갈라져 나온 실제 구현 (완성)

5안 계획서는 **1D 체인 + 코너 오클루전**으로 결론이 나 있었는데, 실제로는
**2D 3x3 정사각 격자**로 갔다. 계획서가 4방향 격자를 기각했던 이유는 전부
*장르* 논거("관찰 게임은 방을 외워야 한다", "2택이라 무게가 있다")였고,
**기술 논거가 아니었다.** 그래서 장르 쪽 전제를 바꾸자 그대로 무효가 됐다.

#### 무엇을 버리고 무엇을 남기나

| | |
|---|---|
| **버린다** | 8번출구식 **2택·되돌아가기** 규칙 — "이상현상이 있으면 왔던 길로" |
| **남긴다** | **이상현상 판별** 그 자체. 이 포폴이 증명하려는 기능은 이쪽이다 |
| **남긴다** | 관찰 → O/X 판정 → 진행도. 다만 나가는 방향은 넷 중 아무거나 |

> 8번출구는 **기반이었지 목표가 아니었다.** 장르는 호러고, 보여줄 것은
> "이상현상을 판별하는 시스템을 구현할 수 있다"는 것이다. 그 기능이 서 있는
> 무대가 직선 복도든 격자든 상관없다면, **무대는 더 나은 쪽을 고르면 된다.**

#### 이 구조가 가져가는 진짜 이득 — 암전의 자리를 재활용이 대신한다

3안에서 방을 리셋하고 새 이상현상을 뽑던 자리는 **암전**이었다. 격자에서는
그 일을 재활용이 맡는다.

```
3안    판정 → 복도 → SeamTrigger → ▓암전▓ → 리셋 + 재추첨 → 페이드인
격자   판정 → 문 열고 옆 칸으로 걸어감 → RecycleTrailingLine()
                                        └ 2칸 뒤에서 조용히: 문 닫기 + 재추첨
```

**목발이 없어지는 게 아니라, 다른 것이 그 일을 대신하게 되는 것이다.**
그래서 덤으로 코드가 준다 — `SeamTrigger` · `FollowActiveRoom`(좌우 슬롯 교대
때문에만 있던 클래스) · 루프용 `ScreenFader`/`PlayerTeleporter` 호출이 전부 없어진다.

#### 칸을 손이 아니라 도구로 세우다

칸 하나에 바닥·천장·벽·문·섬·소품·조명·이상현상까지 합치면 오브젝트가 50개를
넘는다. 좌표를 손으로 찍으면 조금만 어긋나도 증상이 원인과 안 닮게 나타난다
(아래 "겪은 버그" 참고). 그래서 **에디터 전용 도구 두 개**를 만들어 세웠다
(`Assets/_Project/Scripts/Editor/`, 빌드에는 안 들어간다).

| 도구 | 메뉴 | 하는 일 |
|---|---|---|
| **조각 자** (`ModuleRuler.cs`) | `Tools ▸ 조각 자` | 조각의 사본을 원점에 잠깐 세워 실제 크기·피벗·콜라이더를 잰다. 폴더째 재서 표(`.tsv`)로도 뽑는다 |
| **칸 조립기** (`GridCellBuilder.cs`) | `Tools ▸ 칸 조립기` | 실측값을 받아 바닥·벽·문·섬·소품·조명·이상현상을 좌표 계산까지 해서 통째로 배치한다 |

**왜 좌표를 표에 박아두지 않았나 —** 한 변 조각 수 하나만 바꿔도 좌표 수십 개가
전부 무효가 된다. 그래서 조립기는 좌표 대신 **채우는 규칙**(큰 조각부터 욕심껏
채우기, 벽 안쪽으로 들이는 양, 벽면에 등을 붙이는 계산)을 갖고, 치수가 바뀌면
배치가 따라온다.

**어디서 멈췄나 —** 문짝은 자동 배치하지 않는다. 문 부품(`wall_doubledoor_single`
+ `doubledoor_frame01` + `door_01` 두 짝)의 경첩 자리는 에셋의 피벗 규약에 달려
있어 계산으로 확신할 수 없었다. 대신 조립기에 `문간 하나만 만들기` 버튼을 두어
**오브젝트 하나만 보면서 눈으로 맞추고**, 그 결과를 `문간 통짜`로 등록하면
나머지 세 면은 도구가 복제한다. 반복은 도구가, 판단은 사람이 — 추격자를 씬
구조로 푼 것과 같은 선 긋기다.

**"다시 짓기"와 "얹기"를 갈랐다 —** 처음엔 버튼 하나(`칸 만들기`)가 매번 칸을
통째로 새로 지었다. 문제는 `GridCell_v3`가 이미 손으로 다듬은(서랍 위치, 문짝
삭제 등) 프리팹이라, 새 기능 하나 넣자고 다시 지으면 그 프리팹은 그대로 두고
**엉뚱한 새 오브젝트**가 하나 더 생길 뿐이었다. 그래서 `선택한 칸에 진행도
표시만 추가`처럼, **이미 있는 칸을 골라 그 안에서 필요한 것만 찾아 얹는** 버튼을
따로 만들었다 — 나머지는 하나도 안 건드린다. 앞으로 다듬어놓은 칸에 기능을
더할 때는 항상 이 패턴(선택 → 그 안에서 대상 탐색 → 없으면 추가)을 쓴다.

#### 겪은 버그 5종 — 증상과 원인이 하나도 안 닮았다

**① 방향키를 눌러도 안 움직인다 — `Time Scale`이 0으로 커밋돼 있었다**

"벽에 끼인 것 같다"고 느꼈는데 실제로는 **엔진 시간이 멈춰 있었다.**
증상이 '끼임'으로 보인 이유가 `FirstPersonController`의 구조에 있다.

| | `Time.deltaTime` | timeScale이 0이면 |
|---|---|---|
| `HandleLook()` | **안 쓴다** (마우스 델타는 이미 프레임 간 이동량) | 멀쩡히 돈다 |
| `HandleMovement()` | 쓴다 (`Move(velocity * deltaTime)`) | **이동량이 정확히 0** |

그래서 **둘러볼 수는 있는데 걸어지지 않는** 상태가 됐고, 그게 끼임처럼 보였다.
`Time Scale`은 Unity Recorder를 설치하면서 딸려 들어온 것으로 보인다.

> ⚠️ **Project Settings의 Time Scale은 재생 중에 고치면 저장되지 않는다.**
> 그 칸은 재생 중엔 런타임 `Time.timeScale`을 직접 만지는 것이라, 플레이를 멈추면
> 에셋 값으로 되돌아간다. **정지 상태에서 고치고 저장**해야 한다.

**② 벽이 서로를 관통한다 — 칸이 자기 몫보다 컸다**

칸을 `HorrorZip`(3안 건물 전체) **4채를 풍차로 붙여** 만들었는데, 건물 하나가
칸 간격보다 길었다. 그래서 네 채가 중앙에서 서로를 뚫고, 경계 밖으로도 삐져나갔다.

증상은 원인과 전혀 닮지 않았다 — **바닥 한복판에 프레임 없이 선 문짝**,
**천장을 뚫고 나온 형광등**, **영안실 천장과 복도 바닥이 같은 자리에 있는 것**.

| | |
|---|---|
| 소켓 간격 (칸 하나의 몫) | 47.9 × 43.79 |
| 실제 건물 길이 | 약 55 |

**③ 옆 칸으로 넘어갈 수 없다 — 소켓은 문이 아니라 벽이다**

배치 계산은 완벽했다. 칸 A의 북쪽 소켓과 칸 B의 남쪽 소켓이 소수점까지 맞물린다.
그런데 그 소켓 자리가 **복도 끝 막힌 벽**이었다(3안에서 일부러 그렇게 정한 규칙 —
"소켓은 통과하는 문이 아니라 배치 계산용 기준점이다"). 딱 붙긴 정확히 붙었는데
**구멍이 없었다.**

**④ 시체 서랍이 벽을 뚫고 이웃 칸에 튀어나온다 — 벽 두께 예산 초과**

`corpse_drawer`는 몸통 깊이가 **2.188m**다. 3안은 건물이 한 채만 켜져 있어 벽
뒤가 물리적으로 없었으니 뚫고 나가도 아무도 몰랐다. 격자는 벽 뒤가 **이웃
칸**이라, 서랍을 남벽(두께 0.018m)에 붙이는 순간 그 방 안으로 1.7m씩 밀고
들어갔다. `GridDebugPanel`의 크기 줄이 `Z +6.8` 초과로 정확히 이걸 잡아냈다.

일반적인 모듈러 킷 문제라 이름도 있다 — **벽 두께 예산**을 정하면 그보다 깊은
것은 벽에 못 붙인다. 업계 해법은 세 갈래다: 전용 벽감(alcove) 모듈을 만들거나,
방 사이에 서비스 보이드(죽은 공간)를 두거나, 애초에 두꺼운 구조물(서비스 코어)에
넣는다. **섬(4m 두께)이 이미 세 번째였다** — 은폐층·이상현상 무대에 이어 **깊은
설비를 삼키는 코어** 역할까지 겸하게 됐다. 서랍을 섬 남쪽 면에 4열×3단으로
박고(원본 `HorrorZip`을 실측해 그대로 가져온 간격 — 열 1m·단 0.833m), 서랍
뒤(섬 안쪽)를 막는 벽 세 장(`DrawerBox`)을 더해 완전히 가뒀다.

> 3안에서 공짜였던 것(벽 뒤가 없음)이 격자에서 값이 매겨졌고, 그 값을 복도를
> 새로 뚫는 대신 **이미 있던 구조물(섬)**로 치렀다. 추격자 승격·4안 보류에 이어
> **제약을 걷어내면 그 위에 얹혀 있던 것이 하나씩 청구된다**는 주제의 세 번째 사례.

**⑤ 가운데 방에서 나가는 문과 옆 방의 들어가는 문이 같은 경계에 겹친다**

칸마다 사방(N·E·S·W)에 다 문을 달았더니, 두 칸이 만나는 모든 경계에 **문이
두 짝**(각 칸의 문) 서게 됐다. 동쪽으로 나가려고 문을 열면 곧바로 옆 칸의
서쪽 문이 코앞이라, 두 문을 빠르게 연달아 열어버리면 "같은 방을 재활용한다"는
게 아니라 **애초에 문이 이중으로 서 있다는 것** 자체가 눈에 띄었다.

`GridManager`가 칸을 **회전 없이 평행이동만** 하는 성질을 그대로 썼다 — 문짝을
**북·동쪽에만** 달면(남·서쪽은 문틀만 세운다) 모든 경계에 문이 정확히 한 짝만
서게 된다. 대신 재활용 시 문을 닫는 로직(`OnPlayerEnteredCell`)이 **지나온
경계의 문**을 들어온 칸에서만 찾다가, 그 문이 떠나온 칸 소속인 절반의 경우를
놓쳤다 — 양쪽 칸에서 다 찾도록 고쳤다.

> 셋(①~③) 다 `GridManager`가 아니라 **칸(`GridCell`)의 문제**였다. 격자 코드는
> 좌표를 손으로 검산해도 맞았다. **계산이 맞는데 결과가 틀리면, 계산에
> 넣은 것을 의심해야 한다.** ④·⑤는 반대로 **칸이 아니라 격자 자체의 성질**
> (벽 뒤가 실재한다, 평행이동만 한다)에서 나온 것이었다 — 3안의 전제가
> 격자에서 더는 안 지켜지는 자리를 하나씩 찾아내는 과정이었다.

#### 칸 설계 규칙 8개 — 어기면 안 붙는다

`GridManager`는 칸을 **회전 없이 평행이동만** 한다. 이 전제에서 나오는 제약이다.

| # | 규칙 | 어기면 |
|---|---|---|
| 1 | 루트는 원점·무회전 | 전부 어긋난다 |
| 2 | **마주 보는 문은 같은 축 위에** (N·S문의 x가 같고, E·W문의 z가 같을 것) | 이웃 칸 문과 안 맞아 **못 지나간다** |
| 3 | **소켓은 벽 바깥면, 문 정중앙.** N소켓z − S소켓z = 칸 깊이 | 이 값이 그대로 타일 간격이 된다 |
| 4 | 소켓 4개 전부 | `MeasureSpacing()` 실패 + 9칸이 한 자리에 겹침 |
| 5 | **벽·소품이 소켓 면을 절대 넘지 않을 것** | ← ②번 버그. 이웃 칸을 침범한다 |
| 6 | 트리거는 문 안쪽, 로컬 +Z가 방 안쪽 | 진입 판정이 반대로 뒤집힌다 |
| 7 | 문은 **완전히 닫힌 자세로 저장** | `Door`가 그 자세를 '닫힘'으로 굳힌다 |
| 8 | 가운데 섬이 **N-S축과 E-W축을 둘 다** 가릴 것 | 은폐가 없어진다 |

**왜 2번이 '어긋나게'가 아니라 '같은 축'인가 —** 처음엔 문을 좌우로 어긋나게 놓아
시선을 끊으려 했는데, 그러면 이웃 칸과 문이 안 맞는다. 칸이 회전 없이 평행이동만
하므로, A의 북문과 B의 남문이 만나려면 **둘의 가로 위치가 같아야만** 한다.
시선은 문 배치가 아니라 **방 안의 구조물**로 끊어야 한다는 결론이 여기서 나왔다.

**왜 한 변이 벽 조각 × 홀수인가 —** 홀수여야 **가운데 조각이 정확히 중앙**에 온다.
거기에 문을 박으면 마주 보는 문이 저절로 같은 축에 서서 **2번 규칙이 자와 계산 없이
지켜진다.** 짝수면 중앙이 조각과 조각 사이 이음매라 문을 중앙에 못 놓는다.
(Morgue Room PBR은 4m 모듈 → **한 변 20m / 5조각** 채택)

#### 섬 하나가 셋을 겸한다

가운데에 `wall_piece_drawer_01`(시체 서랍 벽) 4장을 정사각으로 세운다.

| 역할 | |
|---|---|
| **은폐층** | 20m 방에서 4m 섬이면 마주 보는 두 문을 완전히 가린다. 북문 어느 지점에서 남문 어느 지점을 보든 그 선은 중앙(x −1~+1)을 지나는데, 섬이 −2~+2를 막고 있다 |
| **이상현상 무대** | `SlideAnomaly`("서랍 전부 열림")가 그대로 산다. 해부대·시체를 얹으면 나머지 3종도 |
| **판정 지점** | 한 면에 키패드(`JudgmentPanel`)를 박으면 관찰과 판정이 한자리에서 끝난다 |
| **깊은 소품 코어** | `corpse_drawer`(깊이 2.188m)처럼 얇은 벽 예산을 훌쩍 넘는 것은 섬 속에만 넣을 수 있다 (겪은 버그 ④ 참고) |

> 뱀서의 3x3에서 **은폐는 카메라가 공짜로 해줬다.** 1인칭은 그 공짜가 없어서
> 은폐층을 직접 만들어야 하는데, 그것을 코너가 아니라 **방 한가운데 놓인 물건**으로
> 풀었다. 어차피 이상현상을 얹을 무대가 필요했으므로 **두 요구가 한 물건으로 합쳐진다.**

#### 조립 순서 — `GridCellBuilder`가 대신한다

10단계 수작업이던 것을 도구 하나로 줄였다. 치수(조각 폭·개수·벽 두께 등)를
넣고 버튼을 누르면 바닥·천장·벽·문틀·섬·소품·조명·이상현상·소켓·트리거·
spawnPoint까지 한 번에 배치하고 `GridCell`의 `sides` 배열까지 자동 배선한다.
사람이 하는 일은 **문짝 하나를 눈으로 맞추는 것**뿐(위 "칸을 손이 아니라
도구로 세우다" 참고). 결과물은 `GridCell_v3` — `GridManager`의 Cell Prefab에
꽂는다.

**옛 `GridCell.prefab`(그리고 v2)은 지우지 않는다.** 새 칸이 잘못돼도 Cell
Prefab만 되돌리면 원상복구다.

#### 합격 기준

`GridDebugPanel`이 이렇게 뜨면 칸 작업이 끝난 것이다.

```
간격  X 20.00   Z 20.00                        ← 간격 = 한 변이어야 한다
크기  실제 20.0 x 20.0   몫 안에 들어옴          ← 초록. 규칙 5의 계측기
연결  소켓 4/4   문 4짝   스폰 O   추격자 1마리   ← 문은 경계당 한 짝(겪은 버그 ⑤)
```

간격이 한 변과 다르게 나오면 **소켓이 벽 바깥면에 안 붙은 것**이다.
**문이 8짝으로 뜨면 남·서쪽에도 문짝이 서 있다는 뜻** — 경계마다 두 짝이 되어
문을 두 번 여는 문제(겪은 버그 ⑤)가 재발한다.

`GridManager`에는 씬 뷰 기즈모(`OnDrawGizmos`)도 붙였다 — 플레이 중 각 칸의
좌표를 라벨로 띄우고, 방금 재활용된 줄을 2초간 빨갛게 칠한다. 재활용은
원래 화면(게임뷰)에 아무 일도 안 일어나야 정상이라 "제대로 도는지"를 눈으로
볼 방법이 따로 필요했다 — 게임뷰는 착시를, 씬뷰는 원리를 보여준다는 이
포폴의 시연 방식을 여기에도 그대로 적용한 것이다.

- **`Grid`의 Cell Swizzle은 XYZ(기본)라 씬 뷰 눈금이 바닥이 아니라 수직면에 그려진다.**

  이유(칸이 제자리에 놓였나)는 표시판이 숫자로 답한다.
- **`SlideAnomaly`는 원래 `RoomModule`(3안)만 찾아 대상을 수집했다.** 격자 칸은
  `GridCell`이라 탐색 범위가 자기 자신으로 쪼그라들어 **0개를 찾고 조용히 아무
  일도 안 일어났다** — "서랍 전부 열림"만 안 나오는 식으로 나타나는 종류라 고치기
  전엔 원인을 짐작하기 어렵다. `FindRoomRoot()`로 분리해 `RoomModule`·`GridCell`
  둘 다 보게 했다(3안 동작은 그대로 유지).
- **경계마다 문이 두 짝이었다.** 칸마다 사방(N·E·S·W)에 다 문을 달았더니, 두 칸이
  만나는 경계엔 양쪽 칸의 문이 겹쳐 서서 **문을 두 번 여는** 문제가 났다. 문짝을

##### ① 3안 경로 제거 — 증거는 코드가 아니라 다른 데 산다

그 증거가 **어디 사는지** 따져보니 코드가 아니었다.

| 증거 | 어디 있나 |
|---|---|
| 3안이 실제로 돌아갔다 | `main` 브랜치에 완성본 통째로 |

| 인터페이스로 묶은 과정 | 커밋 `8ec63b9` |

**지워도 하나도 안 사라진다.** 반대로 남겨두는 값은 실재했다 — `GameManager` 566줄을

##### ② 추격자 — 3번 틀려도 '그것'이 안 나타나는 판이 있었다

"오답 3번 누적되면 다음 칸엔 추격자가 있다"는 규칙이 **실제로는 안 지켜지고
있었다.** 코드를 따라가니 원인이 나왔다.

재활용은 한 번에 **한 줄(3칸)**을 옮기는데, `Dress()`가 그중 **첫 번째 칸**에만
'그것'을 심고 그 자리에서 누적 오답을 0으로 돌렸다. 그 첫 번째가 재배치 루프의
시작점(`i = -1`) 때문에 하필 **플레이어 대각선 칸**이었다.

```
북쪽으로 넘어갔을 때 옮겨지는 세 칸의 새 좌표
   i = -1 → 중앙 + (1, 1)   ← 대각선. 문으로 안 이어진다  ← 여기에 심고 있었다
   i =  0 → 중앙 + (0, 1)   ← 정면. 문으로 곧장 갈 수 있다
   i =  1 → 중앙 + (-1, 1)  ← 대각선
```

대각선 칸은 두 번 움직여야 닿는데, 그 사이 그 칸이 또 재활용되면
`SetAnomaly()`가 표시를 지운다. 벌칙이 **영구히 사라지는** 것이다.

고침은 **두 줄의 조합**이었고, 새 API는 하나도 안 만들었다.

| 고침 | 내용 |
|---|---|
| **정면 칸에만 심는다** | `LastRecycle.to`가 <b>이미 그 정면 칸 좌표</b>다 (뒤처진 줄 대표 좌표 + 방향 × 한 변 == 새 중앙 + 방향). 그대로 비교해서 쓴다 |
| **청산 시점을 옮긴다** | 누적 오답 0으로 돌리는 것을 '심은 순간'에서 **'벌칙이 실제로 도착한 순간'**(추격자가 등장할 때)으로. 표시가 지워져도 다음 재활용에서 다시 심겨 **반드시 도착한다** |

덤으로 하나 더 막았다 — 플레이어가 정면이 아니라 옆으로 돌아 걸으면 전환마다 새
정면 칸에 표시가 생기는데, 옛 표시를 지우지 않으면 **이미 청산된 벌칙이 한 번 더**
집행된다. 씬의 추격자는 한 마리니 표시도 한 칸이어야 한다(`ClearOtherStalkerMarks`).

> **"기억도 안 나는 오류" 쪽은 전부 이미 해결돼 있었다** (위 "추격자 — 씬 구조로 푼
> 문제들" 4종 + 격자 전환 때의 `WorldToCell` 반올림). 지금 애매하게 느껴진 것은
> 남은 버그 하나 때문이었고, 그게 이것이다.

##### ③ N×N 일반화 — 그리고 "왜 3이면 충분한가"

`GridManager`에 3이 **네 군데** 매직 넘버로 흩어져 있었다(생성 범위 ±1, 뒤처짐 2,
이동량 3, 줄 길이 ±1). 읽는 사람은 그 1·2·3의 **관계**를 좌표를 그려가며 복원해야 했다.
한 변을 필드로 빼고 전부 유도값으로 바꿨다.

```
Radius R = (한 변 N - 1) / 2
칸 생성 범위   -R ~ +R
뒤처진 줄      새 중앙 - 진행방향 × (R + 1)
이동량         진행방향 × N          ( = 2R + 1 )
줄 길이        -R ~ +R
```

**이동량이 왜 N인가 —** 옮기기 전 그 줄은 새 중앙 기준 상대좌표 −(R+1)에 있고, 가야
할 자리는 격자의 맨 앞 +R이다. **둘의 차가 곧 N이다.** 숫자를 지우고 이 관계를 적으니
한 변을 5로 바꿔도 같은 코드가 맞는다.

**그래서 답할 수 있게 된 질문 —**

> 재활용되는 줄은 **옮기기 전** 자리가 새 중앙에서 `R+1`칸 뒤에 있다. N=3이면 2칸 —
> 그 사이에 경계가 둘, 닫힌 문이 두 짝 끼어 있어 재배치 순간이 시야에 안 걸린다.
> N=1은 이웃 칸이 아예 없어 격자가 성립하지 않으므로 **3이 최소다.** N=5면 여유가
> 3칸으로 늘지만 칸이 9개에서 25개가 된다(상시 로드 2.8배) — 여유를 더 살 이유가
> 없어서 3으로 둔다.

전에는 "3x3으로 만들었습니다"밖에 못 했다. 지금은 **인스펙터에서 5로 바꿔 실제로
돌려 보여주고 "3이면 충분해서 3으로 뒀다"를 수치로 말할 수 있다.** 기본값 3이라
게임은 그대로다. 짝수를 넣으면 중앙 칸이 안 생기므로 `OnValidate`가 홀수로 보정한다.

##### ④ 은폐 계측 — 주장을 결과로 (`CoverageAudit`)

이 격자의 핵심 주장은 "칸이 등 뒤에서 재배치되는데 화면엔 아무 일도 일어나지
않는다"다. 그런데 그 근거는 **사람이 보고 "안 보이네" 한 것**이 전부였다.

문제는 **안 보이는 사건은 놓쳐도 모른다**는 것이다. 한 프레임 삐져나온 것을 눈으로
잡을 수 없고, 나중에 섬을 옮기거나 문 위치를 바꾸거나 한 변을 키웠을 때 은폐가
깨져도 알 방법이 없다. 서랍 벽뚫림도 결국 **시연 영상을 프레임 단위로 돌려보다**
찾았다.

그래서 이 프로젝트가 **이미 쓰고 있는 방법**을 메인 기능 본체에 적용했다 —
*안 보이는 사고를 숫자로 드러낸다*(커밋 `b099489`의 그 말).

**2단 검사.**

| | 검사 | 근거 |
|---|---|---|
| ① | **차폐 불변식** (결정적, 싸다) | 플레이어 칸에서 그 칸 쪽으로 나가는 **첫 경계의 문이 닫혀 있으면** 그 방향으로는 아무것도 볼 수 없다. 거리나 기하가 아니라 **차폐**로 증명되는 형태라 반박할 여지가 없다 (`GridManager.IsSealedToward`) |
| ② | **시야 판정** (①이 깨졌을 때만) | `Stalker.IsSeenByPlayer()`와 **같은 2단 판정**을 쓴다 — `GeometryUtility.CalculateFrustumPlanes`로 화면 안인지 거르고, `Physics.Linecast`로 벽·문에 가렸는지 본다 |

**표본점을 새로 만들지 않았다 — 칸의 사방 소켓을 그대로 쓴다.** 칸 설계 규칙 3대로
소켓은 *문 정중앙·벽 바깥면*에 있어서 **곧 문간**이고, 칸이 보이려면 반드시 문간을
지나야 하므로 정답 표본이다. 덕분에 **프리팹·씬을 하나도 안 고치고** 붙었다.

다만 소켓을 그대로 쏘면 안 됐다. 두 보정이 **둘 다** 필요했다.

- **안쪽으로 들인다(0.5m)** — 소켓은 벽 바깥면에 붙어 있어 점이 문짝과 같은 평면에
  놓인다. 그러면 Linecast가 그 문을 잡을지가 **부동소수점 운**에 달려, 닫힌 문 뒤인데도
  "보였다"가 나온다. 소켓 forward가 칸 바깥을 향하니 그 반대로 밀면 안쪽이다.
- **눈높이로 올린다(1.6m)** — 소켓이 바닥 높이면 점이 바닥에 가려 **늘 "안 보임"**이
  된다. 검사기가 아무것도 못 잡게 되는 쪽이라 더 위험하다.

**검사 시점은 둘 다다.** 옮기기 **직전**(사라지는 자리)과 **직후**(나타나는 자리)를
각각 본다 — 둘은 다른 사건이라 하나만 두면 반쪽이다.

비용은 **재활용 순간에만** 돈다. 3x3이면 칸 3개 × 소켓 4개 = Linecast 12회, 한 칸
넘어갈 때 두 번. 비워 두면(`GridManager`의 슬롯이 null) 검사만 안 돌고 격자는 그대로
굴러간다 — `GridDebugPanel`과 같은 철학이다.

> ⚠️ **"위반 0회"보다 "검사기가 실제로 잡는지"가 먼저다.** 안 잡히는 검사기의 0회는
> 아무 의미가 없다. 그래서 일부러 깨 보는 절차를 검증에 넣었다 (아래).

##### ⑤ 시연 뷰 — 기즈모는 에디터 밖에서 안 보인다

원리를 보여주는 수단이 둘 있었는데 **둘 다 시연에 못 썼다.**

- `GridManager.OnDrawGizmos()` — **Scene 뷰 전용.** 빌드한 실행 파일엔 아예 없다.
  즉 포폴을 직접 돌려보는 사람에겐 안 보인다
- `GridDebugPanel` — `AnomalyLine()`이 **정답을 그대로 노출**한다. 띄워놓고 녹화하면
  "관찰해서 이상현상을 찾는다"는 게임 자체가 무의미해진다

그래서 같은 표시판 안에 **시연 모드를 따로** 뒀다 (독립 토글).

| | F6 개발 뷰 | F7 시연 뷰 |
|---|---|---|
| 내용 | 간격·크기·연결·**정답**·진행도·추격자 전부 | 격자 그림 + 재활용된 줄 + **은폐 위반 횟수** |
| 정답 노출 | 함 (개발용) | **안 함** |
| 용도 | 버그 추적 | 영상·빌드 시연 |

미니맵도 색을 입혔다 — 내 칸 초록, **방금 재활용된 줄 빨강**(씬 뷰 기즈모와 **똑같은
2초 규칙**: 둘이 서로 다른 줄을 가리키면 뭘 믿어야 하는지 알 수 없다), 없는 칸 경고색.
범위는 `Radius`를 따라가므로 한 변을 5로 바꾸면 그림도 5x5가 된다.

**읽을 데이터는 전부 이미 public이었다** (`Cells` · `CenterCoord` · `LastRecycle` ·
`Radius` + 검사기의 위반 기록). 그릴 것만 추가했다.

이게 켜져 있으면 **게임 화면 하나에 착시와 원리가 같이** 들어온다. 전에는 Scene 뷰와
Game 뷰를 나란히 띄운 2분할 영상이 필요했고, 보는 사람이 어디를 봐야 할지 헷갈렸다.

##### 검증 절차

| # | 확인할 것 | 어떻게 |
|---|---|---|
| 1 | 3안 제거가 아무것도 안 깼다 | 컴파일 통과 · Missing Script 경고 0건 · 걷기·문 E·판정 O/X·진행도·재활용이 전과 같다 · F6 연결 줄이 `소켓 4/4 · 문 4짝 · 스폰 O · 추격자 1마리` |
| 2 | 벌칙이 **반드시 도착한다** | F2(강제 오답) 3번 → 옆 칸으로 넘어가면 **정면 칸**에 '그것'(F6 이상현상 줄). 일부러 옆으로 돌아 몇 칸 더 걸어도 **결국 어느 칸에선 나타난다** |
| 3 | 한 변이 실제로 바뀐다 | `Grid Size`를 5로 → F6의 "칸 N개"가 25, 재활용이 그대로 돌고 못 넘어가는 경계가 없다. 3으로 되돌려 동일한지. 4를 넣으면 경고 뜨고 5로 보정 |
| 4 | **검사기가 실제로 잡는다** | ⓐ 정상 플레이 10칸 이상 → **위반 0회** ⓑ 그다음 일부러 깬다 — 판정 후 문 잠금이 풀리므로 **한 칸에서 여러 문을 열어둔 채** 넘어가 본다 → `Debug.LogError` + 위반 카운터 |
| 5 | 시연 뷰가 정답을 안 보여준다 | F6 끄고 F7만 켜고 녹화 — 게임 화면엔 변화가 없는데 좌표가 통째로 밀려나고 재활용된 줄만 빨갛다 |

> **4번 ⓑ가 왜 "일부러 깨기"로 성립하나 —** 지금 규칙은 *지나온 경계의 문만* 닫는다
> (`OnPlayerEnteredCell`). 판정 후엔 사방 문 잠금이 풀리니, 한 칸에서 **문 두 짝을
> 열어둔 채** 나가면 두 문이 일렬로 뚫린 상태가 만들어진다. 그때 재활용이 보이는지는
> **섬(칸 설계 규칙 8)이 그 시선을 끊는지**에 달려 있어 코드만 읽어서는 단정할 수
> 없다 — 검사기가 답한다. 위반이 나오면 "떠나온 칸의 문을 전부 닫는다"로 규칙을
> 조이면 되고, 안 나오면 **섬이 규칙 8을 실제로 지키고 있다는 증거**가 하나 더 생긴다.
> 어느 쪽이든 **추측이 아니라 계측으로 결론이 난다** — 이 기능을 넣은 이유 그대로다.

#### 📊 렉 미터 이식 — 다른 작업물에서 만든 도구를 가져오다

게임뷰에서 Profiler를 보고 프레임별 기록을 CSV로 남기는 도구(`LagMeter`, 1056줄)를
**다른 포폴 작업물(Momentum, 웹스윙 게임)에서 만들어 뒀던 것**을 이 프로젝트로 가져왔다.
`Unity.Profiling.ProfilerRecorder`로 Profiler 창이 보여주는 값(구간 시간·GC 할당·배치 수)을
**창을 열지 않고 코드에서 직접** 읽는다 — 그래서 **빌드한 실행 파일 안에서도** 숫자가 뜬다.

| 키 | |
|---|---|
| **F8** | 렉 미터 표시 on/off (끈 상태는 다음 Play에도 기억) |
| **F9** | 녹화 시작 / 저장 → `ProfilerCaptures/`에 프레임별 CSV + 한국어 요약 |
| **F10** | 지금 화면을 PNG 한 장으로 → 같은 폴더에 `shot_<날짜시각>.png` |

**F10을 넣은 이유 —** 영상 녹화(Unity Recorder)는 창을 열고 버튼을 눌러야 하고
프레임레이트를 고정해 **성능 수치를 왜곡한다.** 반면 *"어 이상한데"* 싶은 순간은 대개
**한 장으로 충분하다** — 문이 안 닫혔다, 칸이 튀었다, 소품이 벽을 뚫었다. 게다가 표시판이
켜져 있으면 **그 순간의 수치까지 그림 안에 같이 찍혀**, 나중에 "이때 FPS가 뭐였나"를
따로 찾을 필요가 없다.

이식 조건이 좋았다 — 두 프로젝트의 **Unity(`6000.3.14f1`) · URP(17.3.0) · Input System(1.19.0)이
전부 같아서** 마커 이름(`Inl_UniversalRenderTotal` 등)이 그대로 맞았다. 보통 이식에서 제일
말썽나는 자리인데(그 이름은 유니티·URP 버전마다 달라진다) 호환 작업이 없었다.
씬도 안 건드린다 — `[RuntimeInitializeOnLoadMethod]`로 Play 때 스스로 생긴다.

##### 가져오면서 구조를 하나 뒤집었다 — 도구가 프로젝트를 모르게

원본은 재고 싶은 구간 이름을 `CreateRows()` **안에** 적어 뒀다(`PerchPointFinder.Scan`).
그러면 그 파일이 **그 프로젝트 전용**이 되어, 옮길 때마다 목록을 고쳐야 한다.
**고칠 데가 있는 파일은 패키지로 뺄 수 없다.**

그래서 방향을 뒤집었다 — **도구는 자기가 뭘 재는지 모르고, 프로젝트가 등록한다.**

```
LagMeter.cs       내장 항목(물리·스크립트·렌더링·GC·배치)만 안다  ← 어디 떨어뜨려도 손댈 데가 없다
   ↑ RegisterMarker(마커 이름, 표시 이름, 부모)
LagMeterRows.cs   이 프로젝트가 자기 구간을 소개한다            ← 프로젝트마다 이 파일만 다르다
```

순서는 유니티가 보장한다 — 등록은 `BeforeSceneLoad`, 렉 미터 생성은 `AfterSceneLoad`.

##### 이 프로젝트에서 재는 것

복붙만 하면 "FPS 보이는 창"이다. 이 프로젝트의 마커를 꽂아 **격자의 열린 질문에 답하는
계측기**로 만들었다.

| 마커 | 어디에 | 답하는 질문 |
|---|---|---|
| `GridManager.Recycle` | `RecycleTrailingLine()` | ⭐ **재활용 한 번이 몇 ms인가.** 여기가 무거우면 "끊김 없이 걸어서 넘어간다"는 주장 자체가 깨진다 — 지금까지 안 튀는 것을 **눈으로만** 봤다 |
| `└ CoverageAudit.Check` | `Check()` | 은폐 검사(Linecast 12회 × 2)가 먹는 몫 — 주석에 "무시할 만하다"고 써둔 것의 검증 |
| `└ GameManager.Dress` | `Dress()` | 이상현상 복원·발동이 재활용 프레임에 얹히는 몫. 합계만 보면 어느 쪽이 무거운지 모른다 |
| `Stalker.Sight` | `IsSeenByPlayer()` | 위 셋은 한 칸에 한 번이지만 이건 **매 프레임** 돈다 — 상시 비용은 이쪽 |

여기에 내장 **`GC 할당`** 줄이 재활용 프레임의 할당이 0인지 보여준다 —
`movingCells`를 매번 `new`하지 않고 재사용한 그 결정의 근거다(그것도 주석이었을 뿐이다).

> **다음 수 —** `gridSize`를 3과 5로 각각 F9 녹화해 CSV를 비교하면 「왜 3이면 충분한가」가
> 수식(`R+1`칸 여유)에 이어 **수치**로도 채워진다. 한 변을 필드로 뺀 것이 여기서 쓰인다.

##### ✅ UPM 패키지로 떼어냈다 — 이제 이 프로젝트도 패키지를 물고 있다

같은 도구를 앞으로 만들 작업물에도 넣는다면 매번 복사하는 건 답이 아니다. 그래서
별 저장소로 떼어내 **UPM 패키지**로 만들었다.

> **https://github.com/dns7221-web/unity-lagmeter** (태그 `1.0.0`)

이 프로젝트는 이제 `Packages/manifest.json`으로 그걸 물고 있다. `Assets/` 안의 사본은
지웠고, 남은 건 **이 프로젝트 전용 파일 하나**(`LagMeterRows.cs`)뿐이다.

```jsonc
"com.dhs.lagmeter": "https://github.com/dns7221-web/unity-lagmeter.git#1.0.0",
```

**`#1.0.0` 태그를 박은 이유 —** 브랜치로 물면 패키지를 고치는 순간 이 프로젝트가 같이
바뀐다. 포폴은 "어제 되던 게 오늘도 된다"가 중요하므로 버전을 고정하고, 당길 준비가
됐을 때 태그만 올린다.

| 구조 | |
|---|---|
| `package.json` | `com.dhs.lagmeter`. `com.unity.inputsystem`을 의존성에 적어 자동으로 따라오게 |
| `Runtime/` | `LagMeter.cs` + `DHS.Diagnostics.asmdef` |
| `Editor/` | `LagMeterMenu.cs` + `DHS.Diagnostics.Editor.asmdef` (`includePlatforms: ["Editor"]`) |

##### 패키지로 만들면서 실제로 걸린 것 셋

**① asmdef에 `Unity.InputSystem`을 명시해야 한다.** `Assets/` 안의 코드는 암시적으로
모든 패키지를 참조하지만, asmdef를 쓰는 순간 자기 어셈블리가 되어 **직접 적지 않으면
`Key.F8`에서 컴파일 에러**가 난다. 같은 이유로 `autoReferenced: true`도 유지해야 한다 —
끄면 프로젝트의 `LagMeterRows.cs`가 `LagMeter.RegisterMarker`를 못 본다.

**② 에디터 메뉴를 갈라내니 `private`이 깨졌다.** 메뉴를 `Editor/`로 옮기자
`RecordFromStartPrefKey`가 **다른 어셈블리**에서 읽히게 되어 `public`이 되어야 했다.
한 파일에 `#if UNITY_EDITOR`로 섞어둘 때와 달라지는 자리가 정확히 여기 하나였다 —
어셈블리 경계가 생기면 `#if`로는 가려지던 접근 범위가 드러난다.

**③ 전환은 한 번에 해야 한다.** 패키지를 추가하면서 `Assets/`의 사본을 안 지우면
`DHS.Diagnostics.LagMeter`가 **두 번 정의돼 컴파일이 깨진다**(CS0101). 그래서
"manifest 추가 + 사본 삭제"를 같은 커밋에 넣었다.

> **덤 —** 이식할 때 네임스페이스를 프로젝트 이름이 아니라 **최종 이름**(`DHS.Diagnostics`)으로
> 박아둔 덕에 패키지화에서 이름 바꾸는 작업이 0이었다. **다음 단계를 알고 있으면 지금
> 고르는 이름이 달라진다.**

##### Momentum은 전환하지 않는다 (판단)

Momentum에는 아직 자기 사본(`Assets/Project/Scripts/Diagnostics/LagMeter.cs`)이 있다.
그쪽도 패키지를 물게 하면 "고치면 양쪽이 같이 좋아지는" 상태가 되지만, **지금은 하지
않는다.**

Momentum은 이미 영상까지 끝낸 **완성된 포폴**이다. 돌아가는 포폴을 건드리는 것은
얻는 것(사본 하나 줄이기)보다 잃을 위험(멀쩡한 작업물이 깨짐)이 크다. 패키지가 필요해서
만든 것이 아니라 **이 프로젝트가 쓰면서 갈라낸 결과**이고, 그 값은 이미 다 받았다 —
다음 작업물은 복사 대신 git URL 한 줄로 끝난다.

| 한 것 | |
|---|---|

##### ✅ (2026-10-26, 2차 녹화) 범인이 지목됐다 — 그리고 내 추측이 틀렸다

**패키지 `1.3.0`에서 셋으로 줄였다:**

| | |
|---|---|

| `OnTriggerEnter(Collider)` | 복도 중간 트리거 볼륨 통과 감지 |

**설계 포인트 ① — 좌표를 씬에 하드코딩하지 않는다.**
좌·우 슬롯을 손으로 찍어두면 복도 길이를 조금만 바꿔도 전부 다시 재야 한다. 대신
모듈이 자기 접합부(`RoomSocket`)를 **스스로 선언**하게 하고, `MeasureSlots()`가 첫 모듈을
자 삼아 "소켓을 축으로 180° 뒤집은 자리"를 실측해 반대편 슬롯으로 쓴다. 모듈 크기가
바뀌어도 씬을 다시 만질 필요가 없다. (모듈러 레벨 조립의 표준 패턴)

**설계 포인트 ② — 배치 계산은 Transform이 아니라 '값'을 받는다.**
`AlignSeamTo()`의 기준이 되는 소켓은 **바로 그 모듈 자신의** 소켓이다. 살아있는
`Transform`을 참조하면 회전을 적용하는 순간 기준점까지 같이 흔들려 계산이 무너진다.
그래서 위치·회전을 값으로 떠서 넘긴다.

**설계 포인트 ③ — 순간이동의 핵심 함정.**
`CharacterController`는 자기 위치를 스스로 관리해서, 켜진 채로 `transform.position`을
바꾸면 무시되거나 충돌로 튕긴다. → **잠깐 비활성화 후 위치를 옮기고 다시 켜는 것**이
안전한 순간이동의 핵심.

**설계 포인트 ④ — 트리거 위치가 곧 연출.**
`SeamTrigger`를 방문 바로 앞에 두면 나오자마자 암전돼 티가 난다. 복도를 **한참 걷다가**
자연스럽게 걸리도록 문에서 충분히 떨어뜨려야 "걷다 보니 어두워졌다"는 느낌이 산다.

### 4️⃣ 랜덤 이상현상 시스템 — `Anomaly.cs`(추상) + `AnomalyManager.cs`

**기능:** *"시스템은 1개, 변형은 N개"* — 방마다 랜덤으로 이상현상 발동, 리셋 시 항상 정상 복원

| 사용한 함수·API | 용도 |
|----------------|------|
| `abstract class` + `abstract void Activate()/Deactivate()` | 모든 변형의 공통 규격 정의(다형성 기반) |
| `Random.value` / `Random.Range()` | 이상현상 유무·종류 랜덤 결정 |
| `GameObject.SetActive()` (`ToggleAnomaly`) | 시체 소실/증가 (켜고 끄기) |
| `Transform.SetPositionAndRotation()` (`TransformAnomaly`) | 시체 이동/자세 변화 (원래 값은 `Awake`에서 자동 저장) |

**구현된 변형 3종:** 시체 소실 · 시체 이동(자세 변화) · 시체 증가
**설계 포인트:** `AnomalyManager`는 `Anomaly` 타입만 알면 되고, 새 변형을 추가해도 매니저 코드는 그대로. 발동 전 항상 `DeactivateAll()`로 완전 복원해 이전 이상현상이 남는 버그를 원천 차단.

**해결한 이슈 2건:**
- 🐛 **모듈 이동 시 시체가 옛 위치로 튐** — `TransformAnomaly`가 정상 자세를 **월드 좌표**로
  저장하던 문제. 건물이 통째로 옮겨가면 시체는 따라 움직이는데 저장값은 그대로라,
  복원할 때 건물이 있던 옛 자리로 날아갔다. **로컬 좌표** 저장으로 전환해 해결.
- 🐛 **첫 방에는 이상현상이 절대 안 나옴** — `AnomalyManager.Start()`의 `DeactivateAll()`이,
  `GameManager.Start()`가 방금 켜준 첫 방 이상현상을 도로 꺼버리던 문제.
  **`Instantiate`로 생성된 오브젝트의 `Start`는 생성한 쪽의 `Start`보다 늦게 돈다**는 것이
  원인. "이미 세팅됐으면 건드리지 않는다" 플래그를 두어 해결.

### 5️⃣ 판정 UI + 모드 전환 — `JudgmentUI.cs` + `JudgmentPanel.cs` + `InteractionPromptUI.cs`

**기능:** 키패드 상호작용 → O(있음)/X(없음) 판정 → 1인칭 ↔ UI 모드 전환

### 6️⃣ 🎬 중앙 상태 관리 — `GameManager.cs`

**기능:** 진행도(정답 +1 / 오답 0 리셋, 8연속 클리어) · 판정 처리 · 루프 진행 지휘

| 사용한 함수·API | 용도 |
|----------------|------|
| `static Instance` (싱글톤) | 판정 UI·복도 트리거가 쉽게 접근 |
| 상태 필드(`progress` / `judged`) | 진행도 · 중복 판정 방지 |
| `Judge()` → `SetDoorsLocked(false)` → `AdvanceToNextRoom()` → `FadeThrough(DoAdvance)` → `EnterRoom()` | 게임 루프 한 흐름을 한곳에서 조율 |

**설계 포인트 ①:** 각 시스템(문·순간이동·이상현상·페이드)은 자기 일만 하고, **순서와 진행 판단은 `GameManager`가 지휘** → 시스템 간 직접 의존을 줄이고 흐름을 한눈에 파악 가능.

**설계 포인트 ② — 첫 판만은 결국 갈라놓았다.** 원래는 게임 시작과 매 루프가 `EnterRoom()`
하나를 공유했다. "시작할 때만 다르게 도는 경로"가 생기면 첫 판에서만 나는 버그가 따라오기
때문이다(실제로 첫 방 이상현상 버그가 그 종류였다).

하지만 첫 판은 요구사항 자체가 다르다 — 플레이어가 **영안실 안에서** 시작하고, 문은 닫혀
있어야 하며, 이상현상이 없어야 한다(무엇이 '정상'인지 먼저 익혀야 판별이 가능하니까).
공유 경로에 분기를 덧대는 대신 `EnterFirstRoom()`으로 **의도를 이름에 드러내** 분리했다.
경로를 합치는 것 자체가 목적이 아니라, **분기가 숨어드는 것**이 문제였기 때문이다.

**설계 포인트 ③ — 정답을 매니저가 들고 있지 않는다.** "이 방에 이상현상이 있는가"는
`RoomModule.HasAnomaly`가 들고, 매니저는 판정할 때 물어본다. 건물이 2개를 오가는 구조라
매니저에 정답을 캐싱해두면 **어느 건물의 정답인지 어긋나는 순간** 판정이 무너진다.
